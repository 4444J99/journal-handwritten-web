## How the verifier works

- Serves `site/` on 127.0.0.1 (random port), GET/HEAD only, MIME by extension, no directory listing (directories give 404),
  requests resolving outside `site/` (including by symlink) are refused.
- Matrix: {desktop 1280x900 dsf 1; mobile 390x844 dsf 3, `mobile=true`, touch emulation 5 points} x {light, dark}, set with
  `Emulation.setDeviceMetricsOverride` and `Emulation.setEmulatedMedia` (`prefers-color-scheme`).
- Dark assertion: `matchMedia('(prefers-color-scheme: dark)').matches` must equal the cell's expectation.
- Waits for `body.ready` (30 s timeout, failure if missed).
- Records: console `error` and `warning`, `Runtime.exceptionThrown`, `Log.entryAdded` level error, `Network.loadingFailed`,
  responses with status >= 400. Browser-initiated `/favicon.ico` 404s (the page has no icon link) and requests the browser itself
  cancelled (`Network.loadingFailed` with `canceled`) are listed under "ignored" and not counted; no cancelled request occurred in the
  final run. This is a deliberate narrowing of "exit non-zero on any failed request".
- Interaction uses `Input.dispatchMouseEvent`, `dispatchTouchEvent` (mobile) and `dispatchKeyEvent`. The page's own `window.__jc`
  test hooks are used only to locate a tappable item (`tallest`, `centerOn`, `zoom`, `quad`), to read state (`focusKey`, `state`,
  `settled`), and, in the mobile cells,
  to show the bar (`ui(true)`) because the fine-pointer rest path does not apply there. Taps, Escape and button clicks are real input events.
- The DevTools client is in `tools/cdp_client.mjs` (unit-tested without Chrome in `tests/test_cdp_client.mjs`): the connection has a 15 s limit for the WebSocket
  handshake (an endpoint that accepts the TCP connection and never answers is closed and reported, and the limit is cleared once the socket opens so it cannot close
  a working connection), every command has a 30 s limit,
  and when the socket closes or errors every waiting command is rejected at once and later ones are not sent. A Chrome crash
  therefore ends the run with a failing report (each remaining cell records "DevTools connection error") instead of a hang;
  checked once by killing Chrome during a run (exit 1, FAIL, no leftover process). Launching Chrome, connecting to it and the run
  are one cleanup scope (`withBrowser`), so a Chrome that was launched is stopped (SIGTERM) also when the connection to it cannot
  be made; `tests/test_verify_site_cleanup.mjs` runs the verifier against a stand-in "browser" that advertises a DevTools endpoint
  nobody listens on, and against one that accepts the connection and never completes the handshake (`--connect-timeout 500`), and requires exit status 2 and no surviving
  process in both cases (the first failed on the earliest code; the second on the code before the handshake limit existed). The report is written to stdout with
  `writeThenExit`, which exits only after the data has been handed to the operating system; the earlier `process.exit()` right
  after `write()` delivered 131072 of 6291456 bytes through a pipe on this machine.
- Exit status is non-zero on console error, exception, Log error, failed request, HTTP >= 400, failed dark assertion, missing
  `body.ready`, or an exercised check that fails. Warnings are recorded, not failing.

### Method caveats found during the run

- A first run reported the desktop auto-hide as 1.62 s after the pointer left. Cause: the verifier moved the pointer to the bar,
  waited, then left without ever entering the revealed bar, so the page's 2.8 s timer (started at reveal) was already running. The
  verifier now moves the pointer into the revealed bar before leaving; the page behaviour was not changed. The same first run
  counted the favicon 404 as a Log error; it is now classified as ignored.
- Items measured with test hooks (item location, bar display on mobile) depend on `window.__jc` existing in `site/index.html`.
- "Tap outside" and Escape check `focusKey()` returning null after 1.5 s; they do not inspect pixels.
- "No jump to another poem" is not observed. The first tap goes to a far corner, which proves only that focus is released. A second
  tap, aimed at the centre of another poem found through the page's own `quad()` hook, was tried: in three cells that centre lay
  inside the focused poem's box, and in desktop-dark the tap fell inside the focused stack's own area, where `singleTap` toggles the
  controls instead of releasing focus (`site/index.html` `stackHit`, layer box plus a 30-unit pad). The clause rests on reading
  `singleTap` (`site/index.html`, release before hit-test), not on an observation.
- Which poem is picked for the tap tests is not fixed between runs (it was `s385` to `s391` across runs); statuses did not change.
- A first version of the verifier tapped the corner only; the findings of an independent re-run (the "no jump" overclaim, the
  "interrupt" row's qualified PASS, the strip-labels reason, the missing negative half of the pointer-rest rule) are what the
  additions above and in the table respond to.
- Informational: `site/index.html`, which this lane may not change, loads a font family whose name carries the other project's
  name. The public build step in the post-poem lane renames it; the private page is byte-identical to the live v4.

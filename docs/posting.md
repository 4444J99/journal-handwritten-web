# Posting a poem

## Public metadata decisions - 2026-11-06

The author directed completion of these choices. Public builds filter PAL/HF entries to exact selected page/block membership; `post_poem.py` uses this same builder. They blank the journal font's optional provenance/credit name IDs 0 and 10 across platforms (retaining license IDs 13/14), and omit the global machine-transcription review line. The per-line verified gate remains mandatory. Older statements below describing these as pending decisions are historical. Diary1 block 2 now has four manually inspected canonical line regions, with originals retained for archival reconstruction.


`tools/post_poem.py` turns "post a poem" into one small, reviewable action. It checks the poem, builds the public site for it, commits that to a branch of the public repository (`4444J99/versforms`) and opens a pull request. It never merges. Technical document; it contains no editorial content.

## Prerequisites

- Python 3 with Pillow (the standard library is otherwise enough). `git`; `gh` (signed in) for the pull request.
- The font venv, used for one step only (renaming and checking the embedded font): a Python with `fontTools` and `brotli`, at `/Volumes/Archive4T/Runtime/tools/venvs/versforms-font/bin/python` or wherever the environment variable `VERSFORMS_FONT_PYTHON` points. `tools/post_poem.py` and `tools/build_public.py` themselves run under the plain `python3`; they start `tools/font_rename.py` as a subprocess with the venv python. Without the venv the font step cannot run (see "Embedded font" below).
- A studio database export: one JSON file per document at `EXPORT_DIR/COLLECTION/DOCID.json` for the collections `reviews`, `decisions`, `versions`, `release`, `batches`, `rconfig` (the format of the 2026-11-05 export, `exports/studio-db-2026-11-05/`). A collection with no documents may have no folder. `--db` also accepts the directory that contains exactly one `exports/<name>/`. A directory with no collection folder, with several exports, with a document that is not a JSON object, or with **no release documents at all** is a hard stop (otherwise every piece would silently read as "unsorted", which is only a gate that `--force` overrides). The run prints the export directory it resolved and the number of documents per collection. **Every entry of `release/` must be named exactly `p<digits>.json` (lowercase `p`, ASCII digits) and the id must be a piece that exists in `site/data/j.json`.** Anything else is a hard stop that names the entry and that `--force` does not override: a name that only resembles a release document (`P001.json`, `p001.JSON`, `p001 .json`, fullwidth digits, another extension, a stray file, a directory or a link), or one that has the right shape but names no piece (`p0001.json`, `p1.json`, a name padded with zeros, the id of a piece that no longer exists). Such a file would be ignored, its piece would read as unsorted, and the piece could be built and pushed although the ignored file says Reserve. The one tolerated stranger is a regular file named exactly `.DS_Store` (Finder creates it); a directory, a link or another spelling of it stops. A top-level folder that only resembles a collection folder (`release `, `Release.`) is refused the same way, and the check covers every piece, including those already public. **A piece with no release document at all remains the forceable gate (a), "unsorted":** that is the brief's design (unsorted plus `--force`).
- A clone of `4444J99/versforms` (the public repository), clean, on `main`, level with the remote `main`, with exactly one configured origin URL and one effective fetch/push destination: `https://github.com/4444J99/versforms`. An explicit push URL is optional, but multiple or empty URLs, `remote.origin.push`, and enabled or invalid `remote.origin.mirror` are refused. The script builds its commit in a temporary worktree (see "What the script does in the public clone" below); do not use the clone for anything else while a post is open.
- The piece must exist in `site/data/j.json` (ids `p001` to `p126`).

## The command

```
python3 tools/post_poem.py PIECE_ID [PIECE_ID ...] --db EXPORT_DIR --public-repo PATH [options]
```

| Option | Effect |
|---|---|
| `--dry-run` | Checks the input gates and hard stops, then builds and audits the site in the scratch directory; prints the version report, checks, reader-visible strings, warnings, file list and sizes. Writes nothing in the public repository, pushes nothing, leaves `release/public.json` alone. It returns before rendering or writing `pr-body.md`, so it does not exercise the PR-body check. `--public-repo` is optional (without it the repository checks are skipped). |
| `--no-pr` | Creates and commits the branch `post/PIECE_ID` in the public clone (in a temporary worktree: the clone's checkout stays on `main`, untouched) but does not push or open a pull request. It does **not** change the private `release/public.json`; it prints the change to make by hand once the pull request exists. |
| `--force` | Overrides the three gates only (exit code 2 becomes a warning). Never overrides a hard stop. |
| `--include-versions` | Publishes the whole version stack. Needs the author's approval; the script says so. |
| `--accept-shared-scan IDS` | Comma separated ids of co-resident pieces, "other lines" items, or page ids (a facing page of a spread image), whose writing may show in a shared scan. |
| `--accept-embedded-font` | Only for the case where the embedded font cannot be decoded and checked (the font venv is missing) and the page does not name the old family: publish it unchecked. Not needed, and not used, when the check can run; it never covers a font known to carry the old name. |
| `--workdir DIR` | Scratch directory. Default: a new `post-poem-*` directory under `.post-poem-work/` in the private repository (git-ignored). The build is `DIR/build`; a non-dry run writes the pull request text to `DIR/pr-body.md` before committing. A `DIR` that names a file is refused with exit 64. A `DIR/build` that is a symbolic link is refused (exit 64) with a message, never followed or deleted. A `DIR/build` that this script did not make is never deleted: the run is refused (exit 64) unless `DIR` holds the marker `.post-poem-workdir` that the script leaves in a directory it has used. |
| `--source DIR` | Private repository root (default: the repository the script is in). |

Exit codes: `0` done; `2` a gate failed; `3` a hard stop; `64` usage error (including an unknown or missing argument, which argparse would otherwise report as 2); `1` an operation failed part-way (the message says what was left). Unreadable release documents, an unknown id in `release/public.json`, missing `pieces` or `pages` lists in `site/data/j.json`, a build that refuses, and an `index.html` without a title produce a clean hard stop (exit 3). A failure to update the private release list after a successful push and PR creation returns 1 and reports that the PR already exists.

Every post rebuilds the whole public site from `release/public.json` plus the new piece. Pieces that are already public are rebuilt with the same rules (final version only, corrections applied) unless they are listed under `all_versions` in `release/public.json`, which the script writes when `--include-versions` is used. They are not put through the three gates again, but the hard stops "own pool" and "shared scan" run over every piece in the rebuilt list, not only over the requested ones.

## Gates (exit code 2, `--force` can override)

Each prints `PASS` or `FAIL` with the reason. They run for the requested pieces.

1. **(a) In Series.** `release/PIECE.json` exists and its `pool` is `series`. A missing document (in an export that has release documents) is "unsorted", a failed gate that `--force` can override; any pool value that is not exactly `series`, `reserve` or `archive` is a hard stop (below), not a gate.
2. **(b) Fully verified.** Every line of every version block of the piece (`studio/data/review.json`: item, versions, blocks, lines) has a `reviews/LINEID.json` document whose `status` is `confirmed`, or `corrected` with a `text`. This covers all versions, including ones that are not published.
3. **(c) Filed.** The piece id is in the `items` of at least one batch whose `status` is `filed` or `registered` (a draft batch that also lists it does not matter when another batch is filed). A batch counts only if its `items` is a list (a string would make `p001` match inside `p0010`) and its `status` is a string. **This is wider than the brief's wording ("in a GRUW batch marked filed").** The studio's batch life cycle is draft, filed, registered, so a registered batch was filed first, and the studio's own Calendar readiness test (`studio/index.html`, the `ready` condition) accepts both; the gate follows the studio. To require `filed` only, change the one comparison in `gate_filed` (`tools/post_poem.py`) and its test. That is the author's decision.

## Hard stops (exit code 3, `--force` cannot override)

- **Own pool: Reserve, Archive, or anything that is not exactly the studio's value.** If the requested piece's own release pool is `reserve` or `archive`, the post is refused. So is any other value that is not exactly `series`: `Reserve`, ` reserve`, `["reserve"]`, `null`, a number, and even `Series` or `series ` (another case or a trailing space): the script fails safe and refuses them with exit 3 rather than guessing. A value that merely looks like Reserve is never read as "not Reserve"; the message says what it reads like. The same stop applies to every piece already in `release/public.json` whose pool is `reserve`, `archive` or any such value: it would be rebuilt and published again, so the stop names it; take it out of `release/public.json` (and decide how to retire it publicly) before posting anything else. Only a piece with no release document at all is "unsorted": a failed gate (a) for a requested piece, which `--force` can override, and a warning for an already-public piece.
- **(i) Shared scan.** A published page is a whole scan. For each page the published version(s) of each piece in the rebuilt list sit on, every other piece on that page is checked. A spread image is checked as well: when a published page has `sp.f`, the build copies `img/s/<f>.jpg`, the whole two-page spread, so the facing page counts too (pages with the same `sp.k` or `sp.f`, or the page the file is named after); findings there say "facing page of the spread image". A published page without `sp.f` copies no separate spread image, but its own `p`, `i` or `m` scan may still show both halves; whole-spread metadata and byte-identical scan files are checked too. Already in `release/public.json` (or posted in the same run): fine. Pool `series` but not public yet: needs `--accept-shared-scan ID`. **Open question for the author:** accepting it lets a Series piece that has not been posted be readable in the scan of a published page, which sits in tension with the rule that the public site contains only poems marked posted. The flag exists so that the author makes that call each time; this document and the script do not decide it. Accepted piece/item identifiers are printed on the private console, not in the public PR body; the body reports the shared-scan condition without naming unpublished material. Pool `reserve`, `archive`, no release document (unsorted) or any other value: refused, and acceptance does not help. Non-piece "other lines" items from the review data on the page also need acceptance. A facing page with no piece and no review item cannot be shown to be blank: it is refused unless `--accept-shared-scan PAGE_ID` names that page. The published versions select the starting pages for these checks. Pages of unpublished versions are also checked when their writing is visible through a shared spread or a byte-identical scan. The pages whose writing is visible in a scan are found three ways: the spread image of a page with `sp.f` (facing page by the same `sp.k` or `sp.f`, or the page the file is named after; if none can be identified the post is a hard stop); a page whose metadata identifies its own scan as a whole spread (`sp.s` is `whole spread`, or a spread record has no crop box: every other page with the same `sp.k`, as with `diary25` / `diary25a`, whose scan files are byte-identical; a missing key or no identifiable other half is a hard stop); and any page whose `p`, `i` or `m` scan file is byte-identical to one of the published page's. The warning about the piece's own unpublished versions covers these facing pages too, and an already-public piece that has an unpublished version written on a shared scan is warned about. Acceptances are not stored anywhere: every post rebuilds the whole list, so a piece that was posted with `--accept-shared-scan ID` is checked again on every later post, and each later post must pass the same ids again until the accepted piece itself is public.
- **(ii) Stale transcript.** A review document's `original` must equal the current machine reading in `site/data/j.json`. Otherwise the post is refused and the line ids are listed (never the text). Checked for the published blocks of every piece in the rebuilt list.
- **(iii) Unknown piece id.**
- **Public repository preconditions.** There must be exactly one `remote.origin.url`, naming `https://github.com/4444J99/versforms` (optional `.git` and trailing slash; case ignored): scheme https, host exactly `github.com`, no credentials, no port other than 443, no query or fragment, and the exact repository path. ssh forms, `file:` paths, credentials, look-alike hosts (`notgithub.com`, `github.com.example`, `github.com` as a user name) and paths that merely contain the text are refused. An explicit `remote.origin.pushurl` is optional; multiple or empty configured URLs are refused. The effective URLs are enumerated with `git remote get-url --all origin` and `git remote get-url --push --all origin`, which apply `url.*.insteadOf`, `pushInsteadOf` and `pushurl`. There must be exactly one effective URL in each direction, equal to each other, and both must pass the destination check. `remote.origin.push` must not be set. `remote.origin.mirror` must be absent or a valid false value; Git's boolean parser handles forms such as `on` and a valueless setting, and enabled or invalid values are hard stops. Credential-bearing URLs are redacted in diagnostics. The working tree must be clean (untracked files count); the branch must be `main`; local `HEAD` must equal the remote `main` (checked with `git ls-remote`, which writes nothing); the branch `post/PIECE_ID` must not exist locally or on the remote (the detail says which). The working tree is read with `git --no-optional-locks status --porcelain`, so a dry run does not refresh `.git/index`.
- **The other project's name.** The output must not contain the name of the author's music project, in any letter case. Every file in the output is searched as text and as raw bytes (ASCII, which is also the Mac Roman spelling, UTF-16 big endian and little endian), and so is every file and directory name (the log says "output file N: its path" and never repeats the name). Every base64 `data:` URI in a text file is decoded; a font goes through `tools/font_rename.py check`, which searches the decoded `name` table (all platforms, encodings and languages), the CFF font name and top dictionary strings, glyph names, the WOFF2 metadata and the raw bytes of every table; any other payload gets the raw byte search. A compressed WOFF2 stream cannot be searched as raw bytes, so for a font the decoded tables are the authority. Any hit refuses the post. The pull request text is checked the same way before anything is committed.
- **Embedded font that cannot be checked.** Three different cases. (1) The font tool cannot run at all (the venv python is missing, or lacks `fontTools` or `brotli`) and the page does not name the old family: the font cannot be decoded, so the name check cannot cover it. The name check line is then printed as `UNCHECKED` (never `PASS`: the text and raw-byte search ran, the font tables did not). A real run refuses unless `--accept-embedded-font` is given; a dry run only warns (exit 0), because the flag is the way to accept that. (1b) The same, but the page's font family is the old name (as in the live site): the font file is then known to carry the old name and it was not renamed, so a real run is refused and `--accept-embedded-font` does not cover it; install the venv. A dry run fails the same way (exit 3), so a script that reads the exit status is not told that input a real run refuses is fine. With the venv in place the flag is never needed. (2) The venv runs and the font bytes do not parse as a font: nothing vouches for the file (a compressed WOFF2 stream cannot be searched as raw bytes), so this is a hard stop in a dry run and a real run alike, and `--accept-embedded-font` does not cover it.
- **Output checks.** The build must pass its own checks (noindex meta and header, exact title, font family, no source-repository provenance, expected pieces, all images present, no text of an unpublished block anywhere in the output). That last check searches every output text file for each multi-word line of an unpublished block (and page notes), as written and as written inside a JSON string. An occurrence of an unpublished line is excused only when the whole occurrence lies inside an authorized published-line span. The same words outside that span, including an overlapping occurrence that extends past its end, still refuse the post. The structural check on `data/j.json` (every unpublished block empty, every non-empty line a published reading or correction) stays the authority for the data file. A failure here is a bug or a leak; the scratch build remains, but nothing is committed or pushed to the public repository.

## What is published

- **Versions.** Only the final version: the version the author decided as final in the studio's Decisions tab (a `decisions/...-final` document whose `choice` names `PAGE-BLOCK` of that piece), otherwise the top of the piece's stack (`top`, which is also `st[0]`, the version the site shows first). `top` is not always the last entry of `V`; the engine labels `V` oldest to newest, so the last entry is the newest. For each requested piece the script prints which version it publishes (`V[i]` and its id), which is the newest in the stack (`V[n-1]`), which is the top, and how many lines carrying an author correction sit on versions that are not published; the last number is also a warning when it is not zero, because those corrections are not in the public data. `V` carries no dates, so "newest" cannot be derived from dates. A `layers` choice falls back to the top with a warning. Pages used only by unpublished versions are not copied. Blocks of unpublished versions and of other pieces on a published page lose their text, their piece link and their reading note; the scan image still shows the whole page.
- **Corrections.** For each published line whose review status is `corrected`, the line in `data/j.json` is replaced by the author's `text`. Confirmed lines keep the machine reading. Lines of quotation blocks stay withheld: a quotation block (type 4) never takes a correction, in `post_poem.py` and in `build_public.py`, and the count is shown as "withheld".
- **noindex.** `index.html` gets `<meta name="robots" content="noindex">` right after the viewport meta, and a `_headers` file sets `X-Robots-Tag: noindex` for `/*`. An existing robots meta that already contains `noindex` is left as it is (a stricter tag such as `noindex,nofollow` is not weakened); the output check accepts any robots meta containing `noindex`. The empty-release shell written by `tools/build_public.py` carries the same tag, and gets the same `_headers` file. The script never removes `noindex` and its output check fails without it. Removing it is the author's decision. The current `tools/build_public.py` preserves or injects the tag and writes `_headers` for both empty and non-empty builds. The deployment observations in `docs/noindex.md` are dated November 5, 2026; its description of an older non-empty builder dropping the tag does not describe the current code.
- **Title.** The built `index.html` has exactly one title element and its text is `versforms`. The empty-release shell has the same title. `site/index.html` in the source tree is not edited.
- **Font family.** In the built `index.html` every spelling of the old family name (any letter case, with a space, hyphen, underscore or nothing before "Diary", quoted or not: the `@font-face` rule, the hand-font custom property, plain `font-family` values, canvas font strings, the `document.fonts.load` call and visible text) becomes `ajp-scribbles`. The embedded WOFF2 file is renamed too, by `tools/font_rename.py` run with the venv python: name ids 1, 16 and 21 become `ajp-scribbles`, ids 4 and 18 `ajp-scribbles Regular`, id 6 `ajp-scribbles-Regular`, on every record of every platform; every other record or CFF string that carries the old name (ids 0, 3, 5, 7 and others, the CFF font name list and the CFF top dictionary strings) is rewritten; the CFF font name becomes the PostScript name. The font is re-encoded to WOFF2 and its data URI replaced; the font's own `head.modified` time is kept (not the current time), so building the same input twice gives the same bytes and a later post does not show `index.html` as changed when nothing else did. Outlines, cmap and advance widths are not touched (the tests decode the output and compare glyph count, glyph order, cmap, advance widths and table list). A font that does not carry the old name is left alone. The visible sentence in the info panel that names the typeface changes with it; that is reader-visible text, and it is listed in the audit.
- **Source provenance.** `prov.repo`, `prov.commit` and `prov.path` (they name the source repository) are removed from `data/j.json`; `tdate` and `verified` stay. The engine reads `DATA.prov` only in its info panel (`fillInfo`), with a fallback to an empty object and empty strings, so the data loads without them. Static reading only; not run in a browser. Side effects, printed as warnings and listed in the pull request: the info panel's "Scans:" line renders with an empty link and empty commit fields, and while `prov.verified` is false the panel says the machine transcription is "not yet checked by the author", even for a piece that passed gate (b). The build changes the title, font and noindex markup but does not rewrite that information-panel text; the author decides what it should say.
- **Piece numbering.** Piece links in published blocks are renumbered to the public piece list.
- **Unpublished blocks.** A block that is not published keeps no text, no number of lines (its line list is empty), no link to a piece or version, no reading note; the page's per-line boxes (`x`) are kept only for published blocks. The page scan image still shows the whole page.
- **Reader-visible strings.** The dry run and the real run list the title, `aria-label` and `alt` strings, font names (family, full name and the other name records of the renamed font), provenance keys and reading-note counts that the build would publish. It only lists them; the author decides.

Do not regenerate the public `site/` with the bare `python3 tools/build_public.py OUT_DIR`: it has no review database, so it publishes every version with the machine readings (it still keeps noindex, writes `_headers`, sets the title, renames the font, drops the source provenance and renumbers piece links). If the font venv is missing it prints a warning and exits with code 3, because the output would still carry the old font name inside the embedded font. Use `post_poem.py`.

## Does a dry run write nothing?

In the public repository: nothing. The repository checks use `git config`, `rev-parse`, `ls-remote` and `git --no-optional-locks status --porcelain`; none of them writes inside `.git`. The test `test_dry_run_leaves_the_git_index_file_untouched` and `test_dry_run_writes_nothing_and_pushes_nothing` compare the index, refs, working tree and the bare remote before and after. In the private repository: `release/public.json` is untouched; the build and scratch marker go to the scratch directory (`--workdir`, default `.post-poem-work/`, git-ignored). A dry run does not render or write `pr-body.md`; use `--no-pr` with an authorized public clone to inspect the body and committed build without pushing.

## What the pull request contains

Branch `post/PIECE_ID` (several ids are joined with `-`), one commit `Post PIECE_ID` that replaces `site/` with exactly the build output. The pull request body has three lists:

- **What changed**: pieces requested, pieces new in the public site (compared with the public clone's current `site/data/j.json`), already-public pieces rebuilt with changed published data, version published, newest version, top of the stack, corrections on unpublished versions, page ids, files added / changed / removed, bytes.
- **How verified**: every gate and hard-stop outcome once (a forced gate is marked), the output checks, line counts, the sha256 of `data/j.json`.
- **Not verified**: real-device rendering, a Cloudflare preview deploy, the author's sign-off on shared scans, the author's sign-off on the embedded font file's own metadata, font notes (a font that could not be decoded and was accepted unchecked), warnings, and the reader-visible strings list.

No poem text goes into the body, the commit message or the log, and the body never contains the other project's name (it is rendered and checked before the branch is committed; a hit refuses the post). Details about the old font name stay on the console. The name records of the font file (which can hold personal names and a description of where the font comes from) are listed on the console only, as `font file name` rows; the body says so and does not list them. The body marks a check that did not run as `UNCHECKED`.

The private `release/public.json` is changed **only after the branch is pushed and the pull request has been created** (order kept, no duplicates; the write is atomic: a temporary file in the same folder, flushed, then renamed). With `--no-pr`, it is left alone and the intended change is printed to apply by hand. When the push or `gh pr create` fails, it is left alone and the message reports the remaining branch state and PR-body location; that failure path does not print the intended release-list diff. If the private write fails after the PR exists, the script returns 1 and reports the failed update; it does not undo the pushed branch or the PR. The script does not commit or push the private repository: commit that file through the usual private-repository process.

The pull request text omits identifiers of unposted pieces/items accepted through the shared-scan flag, private line IDs from gate details, and page IDs in warnings about unpublished versions on facing pages. The private console retains those details and any `--accept-shared-scan` id that matched nothing. The public body retains the shared-scan condition and verification counts needed for review.

## What the script does in the public clone

- Every Git subprocess receives an environment with inherited repository-location and command-config overrides removed, including `GIT_DIR`, `GIT_COMMON_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`, `GIT_CONFIG`, `GIT_CONFIG_COUNT`/indexed entries and `GIT_CONFIG_PARAMETERS`. The byte-comparison command uses the same boundary. The script does not remove variables from the parent process. Ordinary user authentication and repository configuration remain available and are subject to the destination checks above.
- The script creates its own `post/PIECE_ID` branch from `main`, then builds the commit in a **temporary worktree with detached HEAD** at the reserved base commit. It does not switch the clone's own checkout. `site/` is replaced with the build output and added with `git add -A -f` (a `.gitignore` in the public clone cannot drop a file). The committed paths and file bytes are read through the immutable commit SHA and compared with the build; a clean filter that changes bytes without changing file sizes is refused too. Only after verification does a compare-and-swap advance the reserved branch from its original base to that verified commit. A competing branch update refuses the operation.
- If worktree creation or committing fails (for example, a failing post-checkout/commit hook, signing failure or full disk), cleanup attempts to remove the temporary worktree and only the branch created by this invocation while it still points to the originally owned base commit. A pre-existing branch or a ref moved by another writer is retained. The error reports the branch state and asks for inspection of the checkout after a hook failure. If Git or the filesystem refuses cleanup, inspect and resolve any remaining branch or worktree before retrying.
- The push is `git push --no-follow-tags origin VERIFIED_COMMIT_SHA:refs/heads/post/PIECE_ID`. The immutable source SHA sends only the verified commit even if the local branch moves; the fully qualified destination selects the posting branch, and `--no-follow-tags` prevents an inherited `push.followTags` setting from adding local annotated tags. The script leaves that configuration setting unchanged. The preconditions also reject custom push refspecs and enabled/invalid mirror configuration. After the push, the remote branch must name the commit just made and the remote `main` must be unchanged; if `main` moved, the script reports it and stops.
- If `gh pr create` fails after the push, the message says the branch **is** pushed and prints the exact `gh pr create --repo 4444J99/versforms --base main --head post/PIECE_ID ... --body-file ...` command.
- Regression coverage uses disposable local bare repositories and a fake `gh`. It verifies the posting command's ref selection, environment isolation, cleanup and failure handling; it does not establish real GitHub branch-protection behavior, a successful hosted PR creation, or a deployment. Hooks remain executable local programs, not a sandboxed input: these checks do not prevent an arbitrary hostile hook from changing files or refs on its own.

## Known, and not changed here

- **Page ids are hard-coded in the engine.** Every public build ships `site/index.html`, whose template names pages for two features: the revision-witness table `PAL` (pages `diary13`, `13a`, `14`, `14a`, `53`, `53a`, `54`, `3`, `8`, `8a`, with block indices, belonging to pieces `p020`, `p096`/`p097`, `p004`, `p012`) and the hand-font plates `HF` (`diary21a`, `diary63`, `diary26`, pieces `p032`, `p068`, `p040`). They are ids and structure only, no text, they are in the v4 site already, and the engine skips a page that is not in the data (`BYID[...]` is checked; the hand-font dock lists only pages that exist), but the strings are in the public file. Whether a page id is "metadata" under the rule that unposted pieces never appear online in any form is the author's call; this script does not decide it. Dropping them would mean the build rewriting those two literals (like the title and the font family) and the engine tolerating an empty revision list, which is a change to the engine (the next version of `site/index.html` has to be reconciled with the build's edits anyway). Whether any of those pieces is in Reserve is not visible here: the release documents live in the studio database.
- **The info panel's status line.** The panel (behind the "Information" button) says the machine transcription is "not yet checked by the author" while `prov.verified` is false in `site/data/j.json`. That is one flag for the whole data file, not per piece, so it stays false even for a piece whose every line passed gate (b). The build keeps `prov.verified` as it is; the author decides what that line should say.

## Merging

Review the pull request in `4444J99/versforms`, check the Cloudflare Pages preview when one exists, and merge it yourself. The script never merges.

## Rolling back

In the public repository: `git revert -m 1 MERGE_COMMIT` (or `git revert COMMIT` for a squash or rebase merge) on a new branch, and open a pull request. History is never rewritten or force-pushed. Also take the piece id out of `release/public.json` (and `all_versions`) in the private repository, or the next post will bring it back.

## Tests

For the posting regressions, run `python3 -m unittest discover -s tests -p 'test_post_poem*.py' -v`; the broader Python suite is `python3 -m unittest discover -s tests -v`. The posting tests use synthetic fixtures and disposable local repositories; set `TMPDIR` if scratch files must stay on the external drive. Without the font venv a run on the standard fixture page is refused (its font is known to carry the old name and cannot be renamed), so a test that expected a different outcome is skipped, with a message, when the run it just made was refused for that reason; tests that stop earlier (a failing gate, an unknown piece) and tests that set `NO_VENV` on purpose run either way.

Local CI receipts show skipped counts for Python and Node suites. Set `VERSFORMS_FONT_PYTHON` to an interpreter with both `fontTools` and `brotli` before treating a pass as font/posting coverage. A passing command with skipped tests is incomplete evidence for those skipped cases.
